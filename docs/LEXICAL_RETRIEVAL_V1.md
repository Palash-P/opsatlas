# Lexical Retrieval v1

## Scope

This change adds a second lexical strategy and a second hybrid-fusion mode. It
does not replace either existing implementation:

| Path | Function | Default | Status |
| --- | --- | --- | --- |
| Existing keyword | `keyword_search` | `keyword_strategy="and"` | Unchanged |
| New lexical | `lexical_search` | `keyword_strategy="or_idf"` | Added |
| Existing fusion | `fuse_ranked_results` | `fusion_strategy="chunk"` | Unchanged |
| Source-aware fusion | `fuse_source_ranked_results` | `fusion_strategy="source"` | Added |
| Weighted RRF | `fuse_weighted_ranked_results` | `fusion_strategy="weighted"` | Experimental, opt-in |
| Lexical-primary | `fuse_lexical_primary_results` | `fusion_strategy="lexical_primary"` | Experimental, opt-in |
| Semantic | `semantic_search` | n/a | Unchanged |

`hybrid_search` keeps its original defaults, so existing callers receive the
same AND keyword retrieval and chunk-level RRF as before. The new modes are
selected explicitly:

```python
hybrid_search(
    tenant_id=tenant_id,
    query=query,
    limit=5,
    keyword_strategy="or_idf",
    fusion_strategy="source",
)
```

No schema migration and no new dependency is required. The existing
`chunks_content_fts_idx` GIN index is still the only full-text index.

## Why the AND baseline fails

`keyword_search` uses `websearch_to_tsquery('english', :query)`, which joins every
query term with `&`. On the synthetic corpus no single chunk contains every
lexeme from a natural-language question, so the baseline returns zero chunks for
all 16 scored `golden_v1` queries. The problem is not absence of relevant text;
it is the all-terms-required predicate.

The new strategy changes the predicate to OR and ranks by how much of the query
each chunk covers.

## OR + IDF coverage

`lexical_search` performs one read-only SQL statement with these properties:

1. **OR matching.** Distinct lexemes come from
   `ts_debug('english', :lexical_query)`. A chunk is a candidate when its
   `to_tsvector('english', content)` lexeme array overlaps the query lexeme set,
   or when a recognized identifier matches literally.
2. **Distinct-term coverage.** Coverage is the sum of the IDF weights of the
   query terms that the chunk actually contains. Repeated occurrences of one
   term do not increase the score.
3. **Distinct source-document IDF.** For each lexeme, document frequency is
   `count(DISTINCT document_id)` over the same tenant/active/current-version
   filtered set. It is not `count(*)` over chunks. A source with many chunks
   therefore does not make its vocabulary look artificially common.
4. **Identifier IDF.** Literal identifier matches use the same
   distinct-document-frequency formula, so an identifier that appears in three
   documents is not weighted like one that appears once.
5. **Secondary signals.** Ties are broken by the number of matched distinct
   terms, then `ts_rank_cd`, then `chunk_id`. The `chunk_id` tie-breaker makes
   ranking deterministic for identical coverage and rank scores.
6. **Filters.** Every candidate is restricted by `c.tenant_id`, `d.tenant_id`,
   `d.status = 'active'`, and `dv.is_current = TRUE`. No embedding model or
   embedding-null check is applied, so lexical retrieval remains independent of
   semantic embedding coverage.

The IDF formula is:

```text
idf(term) = ln((N + 1) / (df(term) + 1)) + 1
```

where `N` is the number of distinct source documents in the filtered corpus and
`df(term)` is the number of distinct source documents containing the term. The
`+1` terms keep the weight finite and non-negative.

Lexemes are generated by PostgreSQL's `english` dictionary. They are never
re-stemmed in Python. The OR query used for `ts_rank_cd` is built inside SQL from
the same lexeme set with `quote_literal`, so a stemmed term such as `increas` is
not fed back through the `english` stemmer a second time.

## Identifier handling

The `english` parser splits `PAY-503` into `pay` and `-503`. A bare `503` does
not match `PAY-503`, and `v1` does not match `/api/v1/payments` because that path
is tokenized as one `file` lexeme. `prepare_lexical_query` therefore removes
recognized identifiers from the text before lexeme generation and matches them
literally:

| Kind | Example | Match rule |
| --- | --- | --- |
| `identifier` | `PAY-503`, `PAY-409`, `PAY-400` | Literal token bounded by non-alphanumerics |
| `http_status` | `503` in `HTTP 503` | Standalone 3-digit status; a preceding `-` is rejected, so `PAY-503` is not a status match |
| `api_version` | `v1`, `v2` | Literal `vN` bounded by non-alphanumerics, so `/api/v1/payments` matches and `v10` does not |

Identifiers are not treated as generic numbers. A query containing only
`PAY-503` has no generic lexemes left, but still returns the three documents that
literally contain `PAY-503`. Exact matching is a scope signal, not a relevance
filter: `PAY-503` appears in the payment error runbook, the payments API spec,
and the v3 API spec, so all three can be returned.

`error-code` is not an identifier. It is a hyphenated word, and the `english`
parser produces `error-cod`; the corpus writes “error code”, so a query using
the hyphenated form may still match on `error` and `code`. This is documented
rather than special-cased, because silently rewriting arbitrary hyphenated words
would be a broader behavior change.

### Identifier weighting correction

The first held-out run exposed one lexical miss on
`v2-status-http503-vs-pay503-001`. The question contains both the HTTP status
`503` and the error identifier `PAY-503`. `prepare_lexical_query` correctly
separated them, and `PAY-503` was matched literally. The ranking was still wrong
because the identifier IDF was too small relative to coincidental generic terms:

- `PAY-503` appeared in three current sources, so `df = 3` and
  `idf ≈ 2.0116`;
- one rare generic query term appeared in one source, so `idf ≈ 2.7047` and
  outranked the identifier;
- `runbooks/payment-errors.md` shared `PAY-503` with two other sources and lost
  the `chunk_id` tie-break, placing it eighth.

The correction is explicit and narrow: `lexical_search` multiplies the summed
literal-identifier IDF by `IDENTIFIER_WEIGHT = 2.0`. Identifiers remain ranking
signals. They never filter candidates, and the generic-term, `ts_rank_cd`, and
`chunk_id` tie-breakers are unchanged. With the default weight, the failing query
returns `payment-errors` fourth among unique sources and both expected sources
enter the top five.

The parameter is validated (`identifier_weight > 0`, finite) and recorded in the
report's `retrieval_configuration.lexical.identifier_weight`. Callers can pass a
different positive weight for experiments without changing the default.

## Candidate limit

`lexical_search` and `keyword_search` both accept `limit` in `1..20`.
`hybrid_search` keeps the existing candidate rule:

```text
candidate_limit = min(20, limit * 3)
```

The lexical candidate list is returned directly by `lexical_search`, so the
evaluation can score it independently of either fusion mode. It is not hidden
behind the hybrid result.

## Fusion modes

### Existing chunk-level RRF

`fuse_ranked_results` assigns `1 / (rrf_k + rank)` to each returned chunk. Two
chunks from the same source are two separate candidates and can each contribute.

### Source-aware RRF

`fuse_source_ranked_results` first collapses each candidate list to unique
`(source_key, version_number)` units, keeping the best (lowest) chunk rank for
that source. It then applies `1 / (rrf_k + source_rank)` per source. Chunks from
one source can no longer crowd the fused ranking, and the output records
`semantic_source_rank`, `keyword_source_rank`, and the per-source chunk counts.

Neither mode is selected silently. `hybrid_search` defaults to chunk-level RRF
and requires `fusion_strategy="source"` for the source-aware mode. The evaluation
report contains both `hybrid` and `hybrid_source` rows.

### Experimental: weighted RRF

`fuse_weighted_ranked_results` keeps the same rank-based formula but applies an
explicit weight to each list:

```text
score(chunk) = semantic_weight / (rrf_k + semantic_rank)
             + lexical_weight  / (rrf_k + lexical_rank)
```

`FUSION_WEIGHT_PROFILES` defines the named profiles used by the experiments:

| Profile | Semantic weight | Lexical weight |
| --- | --- | --- |
| `equal` | 1.0 | 1.0 |
| `semantic_heavy` | 2.0 | 1.0 |
| `lexical_heavy` | 1.0 | 2.0 |

The existing equal-weight chunk RRF is untouched: `fuse_ranked_results` still
uses `1/(k+rank)` with no weights, and it remains the baseline and the production
default. Weighted fusion uses the same deterministic order: fused score, best
rank, then chunk ID.

### Experimental: lexical-primary with semantic fallback

`fuse_lexical_primary_results` returns the OR+IDF lexical ranking first and uses
semantic results only to fill remaining top-k slots with unique chunks. Semantic
results never re-rank a lexical chunk. Each result records
`ranking_origin` (`lexical` or `semantic_fallback`) so the evaluation can show
how many slots were filled by each source.

These two strategies are opt-in. `hybrid_search` defaults are still
`keyword_strategy="and"`, `fusion_strategy="chunk"`, and equal weights.

## Duplicate-source investigation

The investigation before this change measured duplicate-source crowding in the
semantic candidate list. Duplicate chunks are common: in the 16-query run, the
semantic top-5 contained chunks from the same source in 14 of 16 queries.
Source-aware fusion reduced that to 0 of 16 by construction.

On `golden_v1` the source-aware and chunk-level rankings were identical for all
16 queries when both used the AND keyword baseline. The reason is that the AND
keyword list was empty, so both modes fused the same semantic list; collapsing
duplicate chunks did not change the order of sources. This is a real result, not
a claim that duplicate crowding never matters. The synthetic corpus is too small
and too source-separable to produce a fusion difference.

## Evaluation

The existing `golden_v1_semantic_vs_hybrid.json` report and the
`golden_v0` dataset/report are unchanged. To produce a comparison report:

```powershell
python scripts/run_retrieval_eval.py `
  --tenant-id <uuid> `
  --dataset evals/datasets/golden_v1.jsonl `
  --source-map evals/datasets/golden_v1.source_map.json `
  --profile evals/datasets/golden_v1.profile.json `
  --include-lexical-comparison `
  --rank-unit source `
  --output evals/reports/golden_v1_lexical_comparison.json
```

`--include-lexical-comparison` scores five retrievers:

1. `semantic`
2. `keyword` (existing AND baseline)
3. `lexical` (OR + IDF coverage)
4. `hybrid` (existing chunk-level RRF with AND keyword)
5. `hybrid_source` (source-aware RRF with AND keyword)

The report adds `aggregate.by_retriever`, `aggregate.category_metrics`, and a
`retriever_comparison` section containing:

- source-level and chunk-level Recall@5, MRR, any-hit@5, and all-expected@5;
- per-category metrics;
- false-positive source rankings (`unmapped` or `version_mismatch`);
- relevant sources found by one retriever but not by semantic top-5;
- queries whose chunk or source ranking differs from semantic;
- duplicate-source counts in the top-5 chunks for every retriever;
- chunk-level versus source-aware fusion differences;
- query-level failures with missing expected sources.

The fusion experiments use a separate opt-in flag so the existing lexical report
is never overwritten:

```powershell
python scripts/run_retrieval_eval.py `
  --tenant-id <uuid> `
  --dataset evals/datasets/golden_v1.jsonl `
  --source-map evals/datasets/golden_v1.source_map.json `
  --profile evals/datasets/golden_v1.profile.json `
  --include-fusion-experiments `
  --rank-unit source
```

`--include-fusion-experiments` scores six retrievers with OR+IDF lexical
candidates: `semantic`, `lexical`, `hybrid` (equal-weight chunk RRF),
`hybrid_weighted_semantic`, `hybrid_weighted_lexical`, and
`hybrid_lexical_primary`. It writes
`evals/reports/<dataset-id>_fusion_comparison.json` by default. The report adds
`fusion_vs_semantic`, `fusion_vs_equal_weight`, per-query fusion contributions,
and ranking-origin counts. See `docs/FUSION_EXPERIMENTS_V2.md` for the full
comparison and recommendation.

## Results on `golden_v1`

The 16 scored queries produced the following source-level metrics. These are
single-dataset observations, not a generalization claim.

| Retriever | Recall@5 | MRR | All-expected@5 |
| --- | --- | --- | --- |
| `semantic` | 0.9688 | 0.8802 | 0.9375 |
| `keyword` (AND) | 0.0000 | 0.0000 | 0.0000 |
| `lexical` (OR + IDF) | 1.0000 | 0.9271 | 1.0000 |
| `hybrid` (chunk RRF, AND) | 0.9688 | 0.8802 | 0.9375 |
| `hybrid_source` (source RRF, AND) | 0.9688 | 0.8802 | 0.9375 |

The lexical strategy recovers the only expected source missed by semantic
retrieval on this dataset (`runbook-postgres-pool-v1` in the multi-document
incident query). Its top-5 source ordering differs from semantic on all 16
queries. The known weak query is `paraphrase-pool-exhaustion-001`: the
postgres-pool runbook is ranked third behind the postmortem and the Kafka
runbook, so the lexical MRR for that query is 0.3333. IDF weighting does not
repair that paraphrase because the query shares more high-IDF vocabulary with
the distractors than with the expected runbook.

The identifier-weighting correction does not change any source-level metric on
`golden_v1`; it was diagnosed and measured on `golden_v2`. The fusion report
`golden_v1_fusion_comparison.json` records the post-correction configuration for
the same 16 queries.

## Held-out queries needed

The 16 scored queries are not enough to support a generalization claim. The
following cases need held-out queries before this strategy is considered for
production selection:

- paraphrases with no shared rare term, especially connection-pool and
  deployment-verification wording;
- queries with more than two expected sources and more than five competing
  sources;
- identifier queries where the identifier appears in several documents and the
  question does not name the expected runbook;
- HTTP status codes that also appear as bare numbers or inside other identifiers;
- API versions beyond `v1`/`v2` and version strings embedded in URLs with
  query parameters;
- non-English text, mixed CJK/Latin identifiers, and Unicode punctuation;
- long questions with many stopwords or repeated terms;
- corpora where one source contributes many chunks in the top-5, so source-aware
  fusion has room to change the ranking;
- tenants with large corpora where the distinct-document IDF differs materially
  from chunk-frequency IDF.

## Limitations

- The evaluation is retrieval-only and uses binary, ungraded relevance.
- Only current versions are searchable; historical ranking is not evaluated.
- The lexical strategy is still lexical. It does not understand synonyms,
  negation, or paraphrases that share no lexeme.
- `ts_rank_cd` is a tie-breaker after IDF coverage, not the primary signal.
- Identifier matching is literal. A renamed identifier or a different
  punctuation style is not normalized.
- No schema or dependency change was made, so the existing GIN index and
  `english` configuration remain the only text-search configuration.
- All reported metrics come from one small synthetic dataset. Treat them as
  diagnostic evidence, not proof of production quality.
